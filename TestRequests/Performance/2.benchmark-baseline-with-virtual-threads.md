```md
# 🚀 Performance Benchmark Report — Virtual Threads Evaluation

---

## 📌 Objective

Evaluate performance improvements after enabling **Virtual Threads** in a Spring Boot application and compare against:

- Blocking (JPA)
- Reactive (WebFlux + Redis)
- Blocking + Virtual Threads

---

## 🛠️ Environment

| Parameter              | Value                         |
|------------------------|------------------------------|
| Backend Framework      | Spring Boot 3.5.14           |
| Java Version           | Java 21                      |
| Database               | PostgreSQL                   |
| Reactive Store         | Redis                        |
| Host                   | localhost                    |
| Virtual Threads        | ✅ Enabled                   |

---

## ⚙️ Test Configuration

| Parameter             | Value                          |
|----------------------|--------------------------------|
| Tool                 | Shell Script (`curl + parallel`) |
| Requests             | 2000 → 5000                    |

| Payload              | `{ "event_type": "test" }`     |

### 🔴 Blocking API (JPA)
```

POST /api/blocking/track

```
### 🟢 Reactive API
```

```
## 📊 Benchmark Results

---

### ✅ Blocking (Before Virtual Threads)

- Total Requests: **2000**
- Total Time: **157114 ms**
- Avg Latency: **78 ms**
- Throughput: **~12 req/sec**

---

### ✅ Blocking (Virtual Threads Enabled, Concurrency 50)

- Total Requests: **2000**
- Total Time: **147324 ms**
- Avg Latency: **73 ms**
- Throughput: **~13 req/sec**

---

### ✅ Blocking (Virtual Threads, Concurrency 100)

- Total Requests: **2000**
- Total Time: **167482 ms**
- Avg Latency: **83 ms**
- Throughput: **~11 req/sec**

---

### ✅ Reactive (High Load)

- Total Requests: **5000**
- Total Time: **404924 ms**
- Avg Latency: **80 ms**
- Throughput: **~12 req/sec**

---

## 📈 Key Observations

---

### ✅ 1. Virtual Threads Improve Blocking Performance

- Reduced latency: **78 ms → 73 ms**
- Improved throughput: **12 → 13 req/sec**

👉 Indicates reduced thread overhead and better scheduling

---

### ✅ 2. Performance Gain is Moderate

- Improvements are incremental (~5–8%)
- No dramatic scaling observed

👉 Reason: system is not fully thread-bound

---

### ✅ 3. Bottleneck Shift Identified

At higher concurrency:

- Latency increases (**73 → 83 ms**)
- Throughput decreases (**13 → 11 req/sec**)

👉 Indicates transition from:

```

Thread-bound → I/O-bound system ✅

```

---

### ✅ 4. Throughput Plateau

Across all tests:

```

\~11–14 req/sec

```

👉 Adding more requests does NOT increase throughput

---

### ✅ 5. Reactive ≈ Blocking + Virtual Threads

- Similar latency (~78–80 ms)
- Similar throughput (~12 req/sec)

👉 Virtual Threads effectively close the gap

---

## 🧠 Key Insights

---

### ✅ 1. Virtual Threads Solve Thread Contention

- Efficient handling of blocking operations
- Reduced cost of thread creation and scheduling

---

### ✅ 2. I/O is the Real Bottleneck

System is limited by:

- DB writes (JPA)
- Redis operations (Reactive)

❌ NOT limited by:
- Thread pool
- Request handling model

---

### ✅ 3. Reactive Benefits are Hidden

Reactive advantages appear only when:

- High concurrency (200+)
- Slow external I/O
- Thread pool exhaustion

---

### ✅ 4. Blocking + Virtual Threads is a Viable Alternative

```

Blocking + Virtual Threads ≈ Reactive ✅

```

Benefits:

- Simpler programming model ✅
- Comparable scalability ✅
- Easier debugging ✅

---

## ⚠️ Limitations

- DB connection pool not tuned
- Local testing environment
- No CPU/memory profiling
- Limited concurrency (≤100)
```

# ✅ 3. Introduce @Async for Parallel Workloads

Use `@Async` when:

* Background processing
* Non-blocking side operations
* Fire-and-forget tasks

***

## ✅ Example

```java

@Async
public void processAsync(Event event) {
    repository.save(event);
}
```

***

## ✅ Enable Async

```java

@EnableAsync
@Configuration
public class AsyncConfig {
}
```

***

👉 Benefit:

    Decouple request latency from long-running tasks ✅

***

# ✅ 4. Custom ExecutorService (Fine-grained Control)

Use custom executor when you need:

* thread pool tuning
* bounded concurrency
* resource isolation

***

## ✅ Example

```java

@Bean
public ExecutorService executorService() {
    return Executors.newVirtualThreadPerTaskExecutor();
}
```

***

## ✅ Use in service

```java
executorService.submit(() ->{
        repository.

save(event);
});
```

***

👉 When to use:

| Scenario              | Preferred         |
|-----------------------|-------------------|
| Simple async          | `@Async` ✅        |
| High control          | ExecutorService ✅ |
| Virtual threads tasks | custom executor ✅ |
